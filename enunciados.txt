EX01: inventario playbook handler idempotencia
==============================================

Tienes un inventario con estos servidores:
	web01
	web02
	db01
Y quieres conseguir el siguiente estado:

Requisitos
	1. Inventario:
		Crea un inventario llamado hosts con:
			web01 y web02 dentro del grupo web
			db01 dentro del grupo db
	2. Playbook
		Crea site.yml
		El playbook debe:
			Ejecutarse únicamente sobre el grupo web.
			Utilizar become.
			Instalar nginx.
			Asegurarse de que el servicio nginx:
				está arrancado
				está habilitado para arrancar automáticamente con el sistema.
	3. Página web
		Crea una página /var/www/html/index.html.
		El contenido debe mostrar:
			"Servidor: web01" en web01.
			"Servidor: web02" en web02.
		No escribas dos tareas distintas para cada servidor. Utiliza una variable o un fact.

	4. Handler:
		Si modificas index.html, nginx debe reiniciarse mediante un handler.
		No queremos reiniciar nginx si el fichero no ha cambiado.
	
	5. Idempotencia
		Ejecuta: ansible-playbook -i hosts site.yml dos veces.
		La primera ejecución debe realizar cambios.
		La segunda debería mostrar algo parecido a: changed=0 en los servidores.

	6. Restricciones:
		Quiero que lo hagas desde cero.
		No necesitas utilizar:
		roles
		Vault
		Collections externas
		Jinja2 avanzado
		Sí quiero que utilices FQCN, por ejemplo: ansible.builtin.copy en lugar de: copy

EX02: 
Partimos del ejercicio 1 y mantenemos la misma infraestructura.
1. CREAR GROUP_VARS
===================

Crear la siguiente estructura:

group_vars/
└── web.yml

Dentro de web.yml debe existir una variable llamada:

web_message

Valor requerido:

Servidor gestionado por Ansible


2. MODIFICAR EL PLAYBOOK
========================

Modificar site.yml para que la pagina web genere dinamicamente:

En lab1:

Servidor: lab1
Servidor gestionado por Ansible

En lab2:

Servidor: lab2
Servidor gestionado por Ansible

La pagina debe utilizar:

- ansible_hostname
- web_message


3. MANTENER LO APRENDIDO EN EX01
================================

El playbook debe seguir incluyendo:

[ ] hosts: web
[ ] become
[ ] FQCN
[ ] Instalacion de nginx
[ ] nginx arrancado
[ ] nginx habilitado
[ ] ansible.builtin.copy
[ ] Handler
[ ] notify
[ ] Idempotencia


4. COMPROBAR LAS VARIABLES
==========================

Antes de ejecutar el playbook, comprobar que Ansible carga la variable.

Comandos:

ansible-inventory -i hosts --graph

ansible-inventory -i hosts --list

Tambien se puede comprobar directamente:

ansible web -i hosts -m ansible.builtin.debug -a "var=web_message"


5. DOCUMENTACION
================

Se permite y se recomienda consultar documentacion oficial.

Buscar especificamente:

Ansible group_vars
Ansible variable precedence


6. RESTRICCIONES
================

No utilizar roles todavia.

No escribir el valor de web_message directamente en site.yml.

No crear una tarea diferente para lab1 y otra para lab2.

El playbook debe funcionar utilizando la misma logica para ambos servidores.

9. VERIFICACION
===============

Ejecutar:

ansible-playbook -i hosts site.yml

Comprobar que no hay errores.

Ejecutar el playbook una segunda vez.

Esperar:

changed=0

si los servidores ya estan en el estado deseado.


EX03 — host_vars y condiciones con when

En los ejercicios anteriores has aplicado la misma configuración a todos los servidores del grupo web.
Ahora vamos a introducir una situación habitual en una infraestructura real:
Los servidores pertenecen al mismo grupo y comparten una configuración base, pero algunos tienen características o necesidades diferentes.

Debes resolverlo utilizando:

host_vars;
variables específicas por host;
condiciones con when.
Infraestructura

Partimos del mismo inventario:

[web]
lab1
lab2

[db]
db01

Seguimos trabajando únicamente sobre:

hosts: web

Por tanto, db01 no debe verse afectado.

Requisito 1 — Crear variables por host

Crea la siguiente estructura:

host_vars/
├── lab1.yml
└── lab2.yml

Cada servidor deberá tener una variable llamada:

web_environment

Los valores serán diferentes:

lab1
production
lab2
development
Requisito 2 — Mostrar el entorno en la página

Modifica la página web para que incluya:

Servidor: <hostname real>
Servidor gestionado por Ansible
Entorno: <valor de web_environment>

Por ejemplo:

Servidor: debian
Servidor gestionado por Ansible
Entorno: production

y en el otro servidor:

Servidor: lab2
Servidor gestionado por Ansible
Entorno: development

Debes seguir utilizando:

ansible_hostname;
web_message;
web_environment.

Requisito 3 — Primera condición

Añade una tarea nueva que solo se ejecute en el servidor cuyo entorno sea production.

La tarea debe crear:

/var/www/html/production.txt

El contenido debe ser:

Este servidor es de PRODUCCION

Para decidir si la tarea se ejecuta o no debes utilizar:

when

No debes crear un playbook diferente.

No debes crear un grupo nuevo.

La decisión debe depender de la variable:

web_environment
Requisito 4 — Condición inversa

Añade otra tarea que solo se ejecute cuando el servidor NO sea de producción.

Debe crear:

/var/www/html/development.txt

con el contenido:

Este servidor NO es de PRODUCCION

También debes utilizar when.

Requisito 5 — Mantener lo aprendido

El playbook debe conservar:

hosts: web;
become: true;
FQCN;
instalación de nginx;
nginx habilitado;
nginx arrancado;
group_vars;
host_vars;
facts;
handler;
idempotencia.
Resultado esperado

Después de ejecutar el playbook:

En lab1

Debe existir:

/var/www/html/index.html
/var/www/html/production.txt

Y no debe existir:

/var/www/html/development.txt
En lab2

Debe existir:

/var/www/html/index.html
/var/www/html/development.txt

Y no debe existir:

/var/www/html/production.txt
⚠️ Pista conceptual importante

when no crea estados por sí mismo.

Si una tarea tiene:

when: web_environment == 'production'

esa tarea simplemente:

production → se ejecuta
development → se salta

Pero piensa en qué ocurriría si:

ejecutas el playbook cuando un host es production;
se crea production.txt;
cambias posteriormente su variable a development;
vuelves a ejecutar.

Este detalle será importante para entender la diferencia entre:

ejecución condicional

y:

gestión declarativa del estado

Por ahora, no tienes que resolver ese caso adicional, pero quiero que observes qué ocurre.

Comprobaciones

Antes de ejecutar el playbook, comprueba las variables.

Puedes probar algo como:

ansible web -i hosts -m ansible.builtin.debug -a "var=web_environment"

Deberías obtener valores distintos según el host.

Después ejecuta:

ansible-playbook -i hosts site.yml

Y comprueba los ficheros:

ansible web -i hosts -m ansible.builtin.command -a "ls -l /var/www/html/"
Estructura esperada al terminar
Certi/
├── apuntes.txt
├── enunciados.txt
├── hosts
├── site.yml
├── group_vars/
│   └── web.yml
└── host_vars/
    ├── lab1.yml
    └── lab2.yml
🧠 Qué debes sacar en claro del EX03

Al terminar debes entender:

group_vars
    ↓
Configuración común para un grupo

host_vars
    ↓
Configuración específica para un host

when
    ↓
Decidir si una tarea se ejecuta según una condición

La progresión hasta ahora es:

EX01 → Mismo estado para todos
EX02 → Configuración común por grupo
EX03 → Diferencias por host + ejecución condicional

EX04 — register, resultados y condiciones basadas en comandos
i==================================================================
Hasta ahora tus condiciones dependen de variables que tú defines:

host_vars
    ↓
web_environment
    ↓
when

Ahora vamos a dar un paso importante:

EJECUTAR UNA COMPROBACIÓN
          ↓
       register
          ↓
 GUARDAR EL RESULTADO
          ↓
        when
          ↓
 TOMAR UNA DECISIÓN

Esto se parece mucho más a la automatización real.

🎯 Objetivo

Crear un playbook que compruebe información real de cada servidor y tome decisiones en función del resultado obtenido.

Seguirás trabajando con:

[web]
lab1
lab2

Requisito 1 — Comprobar si existe nginx

Añade una tarea que compruebe si existe el binario:

/usr/sbin/nginx

Puedes utilizar:

ansible.builtin.command

Guarda el resultado de la ejecución utilizando:

register

La variable de resultado puede llamarse:

nginx_check
Requisito 2 — Mostrar el resultado

Utiliza:

ansible.builtin.debug

para mostrar únicamente el código de retorno del comando.

Debes acceder al resultado almacenado mediante la variable registrada.

Pista conceptual:

register
   ↓
nginx_check
   ↓
nginx_check.rc
Requisito 3 — Condición basada en el resultado

Crea una tarea que solo se ejecute si nginx existe.

La condición debe basarse en el código de retorno (rc) del comando anterior.

La tarea debe mostrar un mensaje similar a:

nginx está instalado en este servidor
Requisito 4 — Condición inversa

Crea otra tarea que solo se ejecute si nginx no existe.

Debe mostrar:

nginx NO está instalado en este servidor

La decisión debe depender del resultado registrado anteriormente.

Requisito 5 — Añadir una comprobación diferente por entorno

Aquí mezclamos EX03 y EX04.

En los hosts de:

production

realiza una comprobación adicional sobre nginx.

En los hosts que no sean production, esa comprobación no debe ejecutarse.

Puedes decidir qué comprobar, pero debe ser una comprobación real ejecutada mediante un módulo y guardar su resultado con register.

Después muestra parte del resultado utilizando debug.

🧠 Concepto central

Hasta ahora:

when: web_environment == "production"

La decisión dependía de un dato que tú habías definido.

Ahora también podrás hacer:

COMANDO REAL
      ↓
RESULTADO REAL
      ↓
register
      ↓
when
      ↓
DECISIÓN

Ejemplo conceptual:

¿Existe nginx?
       │
       ▼
    command
       │
       ▼
      rc=0
       │
       ▼
      when
       │
       ▼
 "nginx instalado"
Restricciones

Debes mantener todo lo anterior:

group_vars;
host_vars;
facts;
when;
handler;
FQCN;
idempotencia.

No necesitas crear un playbook nuevo. Puedes añadir las tareas a site.yml.

Qué debes aprender con EX04

Al terminar debes entender:

register
    ↓
guardar resultado de una tarea

variable_registrada.rc
    ↓
código de retorno

debug
    ↓
inspeccionar resultados

when
    ↓
tomar decisiones con información real

Este ejercicio ya empieza a entrar en un patrón muy habitual en automatización:

COMPROBAR
    ↓
ANALIZAR
    ↓
DECIDIR
    ↓
ACTUAR

Y ese patrón conecta bastante directamente con el troubleshooting que hiciste en la infraestructura real: comprobar SSH/Python, interpretar el resultado y separar los hosts según su comportamiento.

EX05 — Loops (loop) y automatización repetitiva
🎯 Objetivo

Aprender a ejecutar una misma tarea sobre varios elementos sin repetir la tarea manualmente.

Hasta ahora podrías hacer algo así:

- name: Instalar curl
  ansible.builtin.apt:
    name: curl
    state: present

- name: Instalar vim
  ansible.builtin.apt:
    name: vim
    state: present

- name: Instalar tree
  ansible.builtin.apt:
    name: tree
    state: present

Funciona, pero es repetitivo.

Con loop:

UNA TAREA
    +
UNA LISTA
    ↓
REPETIR AUTOMÁTICAMENTE

Requisito 1 — Instalar varios paquetes

En tu mismo site.yml, añade una tarea para instalar estos paquetes:

curl
vim
tree

Debes utilizar:

ansible.builtin.apt

y:

loop

La estructura conceptual es:

- name: Instalar paquetes
  ansible.builtin.apt:
    name: ...
    state: present
  loop:
    - ...
    - ...
    - ...

Dentro del módulo tendrás que utilizar la variable especial:

item
Requisito 2 — Crear varios directorios

Crea los siguientes directorios:

/opt/lab
/opt/lab/logs
/opt/lab/config

Debes utilizar:

ansible.builtin.file

y:

loop

Todos deben tener:

state: directory
Requisito 3 — Crear varios archivos

Dentro de los directorios anteriores, crea estos archivos:

/opt/lab/config/app.conf
/opt/lab/config/database.conf
/opt/lab/logs/app.log

Puedes utilizar:

ansible.builtin.copy

con contenido simple.

Ejemplo conceptual:

app.conf
    ↓
Configuración de aplicación

database.conf
    ↓
Configuración de base de datos

app.log
    ↓
Log inicializado por Ansible

Aquí también debes utilizar:

loop
Requisito 4 — Loop con condiciones

Ahora vamos a combinar EX03 + EX05.

Tienes:

lab1 → producción
lab2 → Development

Instala este paquete en ambos:

htop

Pero instala este otro paquete solamente en producción:

ncdu

Puedes hacerlo con tareas separadas y when, o si quieres experimentar, intentar combinar la lógica con loops.

Requisito 5 — Loop + variables

Este es el pequeño reto del módulo.

En lugar de escribir directamente la lista de paquetes dentro de la tarea, crea una variable en:

group_vars/web.yml

Por ejemplo, conceptualmente:

web_packages:
  - curl
  - vim
  - tree

Después utiliza esa variable en el loop.

La idea es:

group_vars
      ↓
web_packages
      ↓
loop
      ↓
item
      ↓
apt
Resultado esperado

Al terminar deberías poder pensar así:

LISTA
  ↓
loop
  ↓
item 1
item 2
item 3
  ↓
MISMA TAREA EJECUTADA VARIAS VECES

Y tu automatización debería dejar ambos servidores con una estructura similar a:

/opt/lab/
├── config/
│   ├── app.conf
│   └── database.conf
└── logs/
    └── app.log

Con ncdu únicamente en:

lab1 → producción
Restricciones

Mantén todo lo que ya tienes:

group_vars
host_vars
when
register
debug
handler
idempotencia
FQCN (ansible.builtin...)
Concepto central del EX05
Antes:

TAREA 1 → curl
TAREA 2 → vim
TAREA 3 → tree


Ahora:

UNA TAREA
    ↓
loop
    ↓
curl
vim
tree

Mi recomendación: haz primero el requisito 1 y pégame solo esa tarea. No intentes resolver los cinco de golpe; este módulo es para que interiorices muy bien la relación entre loop e item.
