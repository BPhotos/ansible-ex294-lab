MINI DOCUMENTACION - EX01 ANSIBLE
======================================
Fundamentos vistos en el primer laboratorio EX294


1. INVENTARIO
-------------

El inventario define los hosts gestionados por Ansible y permite organizarlos
en grupos.

Ejemplo:

[web]
lab1
lab2

[db]
db01

Si un play contiene:

hosts: web

Ansible trabajara sobre lab1 y lab2, pero no sobre db01.

Idea clave:
    Inventario = donde y sobre quien trabajo.


2. PLAYBOOK -> PLAY -> TASK -> MODULE
-------------------------------------

La estructura conceptual es:

Playbook
  |
  +-- Play
       |
       +-- Task -> Module
       +-- Task -> Module
       +-- Task -> Module

Un play define, entre otras cosas:
- sobre que hosts se ejecuta
- si utiliza privilegios elevados
- que tareas debe realizar

Una task representa una accion.

Un module es el mecanismo de Ansible que realiza esa accion.


3. FQCN
-------

FQCN significa Fully Qualified Collection Name.

Ejemplos utilizados:

ansible.builtin.apt
ansible.builtin.copy
ansible.builtin.service

Durante la preparacion utilizaremos preferentemente FQCN.

Ejemplo:

ansible.builtin.apt:
  name: nginx
  state: present


4. BECOME
---------

become: true

Indica que las tareas necesitan ejecutarse con privilegios elevados en el managed node, normalmente mediante sudo.

No debe entenderse como una opcion que siempre hay que poner, sino como una forma de indicar que una operacion requiere privilegios.

5. FACTS
--------

Ansible puede recopilar informacion del sistema remoto antes de ejecutar las tareas.

Una forma de consultar los facts es:

ansible web -i hosts -m ansible.builtin.setup

Uno de los datos disponibles puede utilizarse como:

{{ ansible_hostname }}

Esto permite que el mismo playbook se adapte a diferentes servidores.

Ejemplo:

content: "Servidor: {{ ansible_hostname }}"

En lab1:

Servidor: lab1

En lab2:

Servidor: lab2


6. VARIABLES Y JINJA2
---------------------

Las variables permiten utilizar informacion dinamica en lugar de escribir valores fijos.

La sintaxis basica utilizada en este ejercicio es:

{{ variable }}

Ejemplo:

{{ ansible_hostname }}

Jinja2 se utiliza para interpolar y generar contenido dinamicamente.

En este primer laboratorio solo hemos utilizado una forma sencilla de Jinja2. Su estudio avanzado se realizara posteriormente.


7. MODULE COPY
--------------

ansible.builtin.copy permite copiar archivos o generar contenido.

En el ejercicio se utilizo:

ansible.builtin.copy:
  content: "Servidor: {{ ansible_hostname }}"
  dest: /var/www/html/index.html

La opcion content permite generar directamente el contenido del archivo.

Esto evita tener que crear manualmente un index diferente para cada servidor.


8. HANDLERS
-----------

Los handlers son tareas especiales que se ejecutan cuando una task las notifica mediante notify.

Ejemplo:

Task:

- name: Crear pagina web
  ansible.builtin.copy:
    content: "Servidor: {{ ansible_hostname }}"
    dest: /var/www/html/index.html
  notify: reinicia nginx

Handler:

handlers:
  - name: reinicia nginx
    ansible.builtin.service:
      name: nginx
      state: restarted

Conceptualmente:

TASK
 |
 +-- no cambia -> no handler
 |
 +-- cambia ----> notify -> HANDLER

El nombre de notify debe coincidir con el nombre del handler.

Error cometido durante el laboratorio:

notify: reinicia apache

Handler:

name: reinicia nginx

Resultado:

The requested handler 'reinicia apache' was not found

La correccion fue hacer coincidir ambos nombres.


9. IDEMPOTENCIA
---------------

Una de las ideas fundamentales de Ansible.

El objetivo no es ejecutar comandos repetidamente, sino conseguir que el sistema alcance un estado deseado.

Ejemplo:

ansible.builtin.apt:
  name: nginx
  state: present

Primera ejecucion:
    changed

Siguiente ejecucion:
    ok

En el laboratorio:

lab1 : changed=0
lab2 : changed=0

Esto demuestra que el sistema ya estaba en el estado declarado y Ansible no realizo cambios innecesarios.

Idea clave:

NO:
    "Ejecuta este comando."

SI:
    "Quiero que el sistema este en este estado."


10. SERVICIOS
-------------

ansible.builtin.service permite gestionar servicios.

Ejemplo:

- name: Configurar nginx
  ansible.builtin.service:
    name: nginx
    state: started
    enabled: yes

state: started
    Garantiza que el servicio este arrancado.

enabled: yes
    Garantiza que el servicio este habilitado para arrancar con el sistema.


11. TROUBLESHOOTING
-------------------

Ansible proporciona informacion muy util cuando una tarea falla.

Proceso recomendado:

1. Leer el error completo.
2. Identificar la TASK que falla.
3. Revisar que intenta hacer.
4. Revisar modulo y parametros.
5. Revisar variables.
6. Revisar nombres.
7. Revisar YAML e indentacion.
8. Corregir.
9. Ejecutar de nuevo.
10. Verificar el resultado.

Ejemplo real del laboratorio:

The requested handler 'reinicia apache' was not found

La causa no era nginx ni SSH.

Era una discrepancia entre:

notify: reinicia apache y name: reinicia nginx

Esto es troubleshooting basico de Ansible.


12. DOCUMENTACION
-----------------

No es necesario memorizar toda la sintaxis.

Durante la preparacion:

1. Intentar resolver.
2. Consultar documentacion oficial si falta sintaxis.
3. Aplicar la informacion encontrada.
4. Ejecutar.
5. Analizar el resultado.

La habilidad importante es saber que concepto/modulo necesitas y encontrar rapidamente la informacion correcta.


13. MODELO MENTAL
-----------------

Cuando recibas un problema de Ansible, pensar:

    ¿Sobre que servidores? --> INVENTARIO --> ¿Que estado quiero? --> PLAY --> ¿Que Acciones? --> TASK --> ¿Que modulo? --> MODULE --> ¿Necesito datos dinamicos? --> FACTS / VARIABLES --> ¿Una tarea cambia algo? --> NOTIFY --> HANDLER --> ¿Es idempotente? --> EJECTUAR DE NUEVO.

# EX02 - VARIABLES, GROUP_VARS Y FACTS
======================================

El objetivo de este ejercicio ha sido aprender a separar la configuración y los datos de la lógica del playbook.

En lugar de escribir toda la información directamente dentro de site.yml, una parte de la configuración se almacena en una variable externa.

## ESTRUCTURA FINAL

Certi/
├── apuntes.txt
├── enunciados.txt
├── group_vars/
│   └── web.yml
├── hosts
└── site.yml

## GROUP_VARS

Ansible permite definir variables asociadas a grupos del inventario.

Si en el inventario existe:

[web]
lab1
lab2

Podemos crear:

group_vars/web.yml

Las variables definidas dentro de ese archivo estarán disponibles automáticamente para los hosts pertenecientes al grupo web.

## VARIABLE UTILIZADA

En group_vars/web.yml:

	---
	web_message: "Servidor gestionado por Ansible"

Esta variable se puede utilizar posteriormente desde el playbook: {{ web_message }}

## SEPARACION DE CONFIGURACION Y LOGICA

Antes:

site.yml
|
+-- Contenido fijo
+-- Lógica del playbook

Ahora:

group_vars/web.yml
|
+-- Datos / configuración

site.yml
|
+-- Lógica / automatización

Esto permite que los playbooks sean más mantenibles.

Si necesitamos modificar el mensaje, podemos hacerlo sin modificar la lógica del playbook.

## USO DE VARIABLES

Las variables se utilizan mediante Jinja:

{{ nombre_variable }}

Ejemplo:

{{ web_message }}

## FACTS DE ANSIBLE

Ansible recopila información sobre los hosts remotos durante:

Gathering Facts

Una de esas variables es:

ansible_hostname

Ejemplo:

{{ ansible_hostname }}

Esta variable devuelve el hostname real configurado en el sistema remoto.

## VARIABLE PROPIA + FACT

En el ejercicio se combinaron:

ansible_hostname y web_message

para generar dinámicamente el contenido de:

/var/www/html/index.html

DIFERENCIA IMPORTANTE:
INVENTORY HOSTNAME VS ANSIBLE_HOSTNAME
--------------------------------------

Durante el ejercicio se descubrió que nombre del host en el inventario no siempre es igual a ansible_hostname

Ejemplo:

INVENTARIO              HOSTNAME REAL
---
lab1                    debian
lab2                    lab2

Por tanto:

lab1 es el nombre utilizado por Ansible dentro del inventario.
Mientras que ansible_hostname representa el hostname configurado realmente en el sistema operativo remoto.

## COMPROBAR VARIABLES

Podemos comprobar directamente una variable utilizando:

ansible web -i hosts -m ansible.builtin.debug -a "var=web_message"
Esto permite verificar que Ansible está cargando correctamente la variable.

Resultado esperado:

lab1 → Servidor gestionado por Ansible
lab2 → Servidor gestionado por Ansible

## COMPROBAR EL INVENTARIO
Podemos visualizar la estructura del inventario:

ansible-inventory -i hosts --graph

También podemos obtener una representación completa:
ansible-inventory -i hosts --list

## GENERAR CONTENIDO DINAMICO

El módulo copy permite generar un archivo utilizando variables.

Ejemplo conceptual:

ansible.builtin.copy:
content: "Servidor: {{ ansible_hostname }}\n{{ web_message }}"
dest: /var/www/html/index.html

## IMPORTANTE: SALTOS DE LINEA

Durante el ejercicio apareció un problema con el salto de línea.

Se utilizó: \\n Esto provocó que el contenido generado mostrase literalmente: Servidor: lab2\nServidor gestionado por Ansible

Para generar un salto de línea real debe utilizarse: \n

VERIFICACION DEL RESULTADO REAL
-------------------------------

Un PLAY RECAP correcto no significa necesariamente que el resultado final sea exactamente el esperado.
Después de ejecutar el playbook se comprobó el contenido real: ansible web -i hosts -m ansible.builtin.command -a "cat /var/www/html/index.html"

Esto permitió descubrir:

1. Que el salto de línea se estaba escribiendo incorrectamente.
2. Que lab1 y ansible_hostname no tenían el mismo valor.

LECCION IMPORTANTE
------------------

No debemos considerar un playbook correcto únicamente porque: failed=0

También debemos comprobar que el estado final del sistema es realmente el esperado.

HANDLERS
--------

Se mantuvo el handler aprendido en EX01.

La tarea que modifica index.html notifica al handler: notify: reinicia nginx

El handler solamente se ejecuta cuando la tarea produce un cambio.

Si index.html no cambia:

	- la tarea devuelve ok;
	- no se ejecuta el handler;
	- nginx no se reinicia.

IDEMPOTENCIA
------------

Primera ejecución:

La página web cambió.

Por tanto:

	- la tarea copy produjo changed;
	- se notificó el handler;
	- nginx se reinició.


Segunda ejecución: changed=0

Esto demuestra que el playbook es idempotente.

El estado deseado ya estaba configurado y Ansible no realizó cambios innecesarios.

# EX03 - HOST_VARS Y TAREAS CONDICIONALES

## OBJETIVO

Aprender a utilizar variables específicas por host y tomar decisiones diferentes dentro del mismo playbook.

Hasta ahora se utilizaban variables comunes para todos los servidores de un grupo mediante:

group_vars/

## ESTRUCTURA

Para definir variables específicas de cada host:

host_vars/
├── lab1.yml
└── lab2.yml

Ejemplo:

host_vars/lab1.yml

---

web_environment: "producción"

host_vars/lab2.yml

---

web_environment: "Development"

## VARIABLES POR GRUPO VS VARIABLES POR HOST

group_vars:

Una variable se aplica a todos los hosts del grupo.

Ejemplo:

group_vars/web.yml

---

web_message: "Servidor gestionado por Ansible"

host_vars:

Una variable se aplica únicamente al host cuyo nombre coincide con el archivo.

Ejemplo:

host_vars/lab1.yml

---

web_environment: "producción"

host_vars/lab2.yml

---

web_environment: "Development"

## COMPROBAR VARIABLES

Se puede comprobar el valor de una variable con:

ansible web -i hosts -m ansible.builtin.debug -a "var=web_environment"

## USO DE VARIABLES EN EL PLAYBOOK

Las variables se utilizan mediante Jinja:

{{ variable }}

Ejemplo:

content: "Servidor: {{ ansible_hostname }}
{{ web_message }}
{{ web_environment }}"

## TAREAS CONDICIONALES

Ansible permite ejecutar tareas únicamente cuando se cumple una condición mediante:

when:

Ejemplo:

* name: Crear archivo de producción
  ansible.builtin.copy:
  content: "Este servidor es de PRODUCCIÓN"
  dest: /var/www/html/production.txt
  when: web_environment == "producción"

La tarea solo se ejecutará cuando la variable tenga ese valor.

## CONDICIÓN INVERSA

También se puede ejecutar una tarea cuando la condición NO se cumple:

* name: Crear archivo de desarrollo
  ansible.builtin.copy:
  content: "Este servidor NO es PRODUCCION"
  dest: /var/www/html/development.txt
  when: web_environment != "producción"

## OPERADORES IMPORTANTES

Igual:

==

Distinto:

!=

Ejemplos:

when: web_environment == "producción"

when: web_environment != "producción"

## RESULTADO POR HOST

El mismo playbook puede comportarse de forma diferente dependiendo de las variables de cada host.

Ejemplo:

lab1
│
└── web_environment = producción
│
└── production.txt

lab2
│
└── web_environment = Development
│
└── development.txt

## SKIPPING

Cuando una condición when no se cumple, Ansible muestra:

skipping

Esto no es un error.

Significa:

La tarea existe
↓
Ansible evalúa la condición
↓
La condición es falsa
↓
La tarea no se ejecuta

## CONCEPTO PRINCIPAL DEL EX03

Un único playbook puede gestionar diferentes servidores de forma diferente.

La lógica es:

Variables
↓
Identificar características del host
↓
when
↓
Ejecutar únicamente las tareas necesarias

## CONCEPTOS APRENDIDOS

* group_vars
* host_vars
* Variables específicas por host
* Variables comunes por grupo
* Uso de {{ variable }}
* when
* ==
* !=
* Tareas condicionales
* skipping
* Diferente comportamiento por host utilizando el mismo playbook

## IDEA PRINCIPAL

No es necesario crear un playbook diferente para cada servidor.

Se puede utilizar:

Un mismo playbook
+
Variables diferentes
+
Condiciones

para adaptar la automatización a cada host.


# EX04 - REGISTER, RESULTADOS Y DECISIONES

## OBJETIVO

Aprender a ejecutar una comprobación, guardar el resultado y utilizar esa información para tomar decisiones dentro del playbook.

El patrón principal es:

COMPROBAR
↓
EJECUTAR
↓
REGISTER
↓
ANALIZAR RESULTADO
↓
WHEN
↓
ACTUAR

## REGISTER

register permite guardar el resultado de una tarea dentro de una variable.

Ejemplo:

* name: Comprobar si existe nginx
  ansible.builtin.command:
  cmd: ls -lrt /usr/sbin/nginx
  register: nginx_check

Después de ejecutar la tarea, Ansible guarda el resultado en:

nginx_check

## EL RESULTADO DE REGISTER

Una variable registrada no contiene únicamente un resultado simple.

Puede contener información como:

nginx_check
│
├── rc
├── stdout
├── stdout_lines
├── stderr
├── stderr_lines
├── changed
├── failed
├── cmd
├── start
├── end
└── delta

## CODIGO DE RETORNO

El campo:

rc

significa Return Code.

Normalmente:

rc = 0

significa que el comando se ejecutó correctamente.

Ejemplo:

* name: Mostrar código de retorno
  ansible.builtin.debug:
  msg: "{{ nginx_check.rc }}"

Si el resultado es:

msg: 0

significa que el comando terminó correctamente.

## USAR REGISTER CON WHEN

El resultado de una tarea puede utilizarse posteriormente en una condición.

Ejemplo:

* name: nginx está instalado
  ansible.builtin.debug:
  msg: "nginx esta instalado en este servidor"
  when: nginx_check.rc == 0

## CONDICIÓN INVERSA

También se puede actuar cuando el resultado es diferente.

Ejemplo:

* name: nginx no está instalado
  ansible.builtin.debug:
  msg: "nginx no esta instalado en este servidor"
  when: nginx_check.rc != 0

## FLUJO

Comando
↓
register
↓
nginx_check
↓
nginx_check.rc
↓
when
│
├── rc == 0
│       ↓
│    Ejecutar acción
│
└── rc != 0
↓
Ejecutar otra acción

## DEBUG

debug permite inspeccionar valores y variables.

Mostrar un valor concreto:

ansible.builtin.debug:
msg: "{{ nginx_check.rc }}"

Mostrar una variable completa:

ansible.builtin.debug:
var: comprobacion

Es especialmente útil utilizar:

var:

cuando todavía no sabemos qué campos contiene una variable registrada.

## EJEMPLO DE COMPROBACIÓN REAL

Comprobar la versión de nginx:

* name: Comprobar versión de nginx
  ansible.builtin.command:
  cmd: nginx -v
  register: comprobacion

Posteriormente:

* name: Mostrar resultado
  ansible.builtin.debug:
  var: comprobacion

## RESULTADO OBTENIDO

La variable registrada puede contener:

changed
cmd
delta
failed
rc
stdout
stderr

En la comprobación:

nginx -v

se obtuvo:

rc: 0

stderr: "nginx version: nginx/1.26.3"

stdout: ""

IMPORTANTE:

No todos los comandos escriben su información en stdout.

Algunos comandos escriben información en:

stderr

Por eso es recomendable inspeccionar primero el resultado completo mediante:

ansible.builtin.debug:
var: comprobacion

Después se puede acceder directamente al campo necesario:

{{ comprobacion.rc }}

{{ comprobacion.stdout }}

{{ comprobacion.stderr }}

## COMBINAR VARIABLES Y REGISTER

Se pueden combinar condiciones basadas en variables con resultados reales.

Ejemplo:

* name: Comprobar versión de nginx en producción
  ansible.builtin.command:
  cmd: nginx -v
  register: comprobacion
  when: web_environment == "producción"

Después:

* name: Mostrar comprobación
  ansible.builtin.debug:
  var: comprobacion
  when: web_environment == "producción"

## CONDICIONES COMPUESTAS

Se pueden combinar varias condiciones mediante:

and

Ejemplo:

when: nginx_check.rc == 0 and web_environment == "producción"

La tarea solo se ejecutará si ambas condiciones son verdaderas.

## FLUJO FINAL DEL EJERCICIO

lab1

web_environment = producción
↓
nginx -v
↓
register: comprobacion
↓
debug
↓
Mostrar información

lab2

web_environment = Development
↓
when = false
↓
skipping

## COMMAND Y CHANGED

Cuando se utiliza:

ansible.builtin.command

Ansible puede mostrar:

changed

aunque el comando únicamente haya realizado una comprobación.

Esto ocurre porque command ejecuta un comando, pero no conoce automáticamente si dicho comando ha modificado el estado real del sistema.

Por tanto:

changed

en una tarea command no siempre significa que el sistema haya cambiado.

# EX05 - LOOPS Y AUTOMATIZACIÓN REPETITIVA

## OBJETIVO

Aprender a ejecutar una misma tarea varias veces utilizando:

loop

El objetivo de un loop es evitar repetir varias tareas iguales.

En lugar de:

* Instalar curl
* Instalar vim
* Instalar tree

Se puede utilizar:

Una tarea
+
Una lista
↓
loop

## LOOP SIMPLE

Ejemplo:

* name: Instalar varios paquetes
  ansible.builtin.apt:
  name: "{{ item }}"
  state: present
  loop:

  * curl
  * vim
  * tree

Durante cada iteración:

item = curl

item = vim

item = tree

## FLUJO

loop
│
├── item = curl
│       ↓
│     apt instala curl
│
├── item = vim
│       ↓
│     apt instala vim
│
└── item = tree
↓
apt instala tree

## ITEM

item es la variable que representa el elemento actual del loop.

Ejemplo:

loop:

* curl
* vim
* tree

En cada vuelta:

{{ item }}

representa uno de los elementos de la lista.

## CREAR DIRECTORIOS CON LOOP

También se puede utilizar loop para crear varios directorios.

Ejemplo:

* name: Crear varios directorios
  ansible.builtin.file:
  path: "{{ item }}"
  state: directory
  loop:

  * /opt/lab
  * /opt/lab/logs
  * /opt/lab/config

En este caso:

item = /opt/lab

item = /opt/lab/logs

item = /opt/lab/config

## LOOP CON LISTAS DE DICCIONARIOS

Cuando cada elemento necesita más de un dato, se puede utilizar una lista de diccionarios.

Ejemplo:

loop:

* ruta: /opt/lab/config/app.conf
  contenido: "Configuración de la aplicación"

* ruta: /opt/lab/config/database.conf
  contenido: "Configuración de la base de datos"

* ruta: /opt/lab/logs/app.log
  contenido: "Logs inicializados por Ansible"

Cada item contiene:

item
│
├── ruta
└── contenido

Por tanto se puede acceder a:

{{ item.ruta }}

{{ item.contenido }}

## EJEMPLO COMPLETO

* name: Crear varios archivos
  ansible.builtin.copy:
  content: "{{ item.contenido }}"
  dest: "{{ item.ruta }}"
  loop:

  * ruta: /opt/lab/config/app.conf
    contenido: "Configuración de la aplicación"

  * ruta: /opt/lab/config/database.conf
    contenido: "Configuración de la base de datos"

  * ruta: /opt/lab/logs/app.log
    contenido: "Logs inicializados por Ansible"

## IMPORTANTE: ESTRUCTURA DE DICCIONARIOS

Esto es INCORRECTO:

* ruta: /opt/lab/config/app.conf
* contenido: "Configuración"

Porque crea dos elementos diferentes:

item 1
└── ruta

item 2
└── contenido

Esto es CORRECTO:

* ruta: /opt/lab/config/app.conf
  contenido: "Configuración"

Porque ambos valores pertenecen al mismo item:

item
├── ruta
└── contenido

## PARAMETROS DE UN MODULO

Los parámetros de un módulo no llevan guiones.

INCORRECTO:

ansible.builtin.copy:

* content: "..."
* dest: "..."

CORRECTO:

ansible.builtin.copy:
content: "..."
dest: "..."

## LOOP + WHEN

Un loop puede combinarse con condiciones.

Ejemplo:

* name: Instalar paquete solo en producción
  ansible.builtin.apt:
  name: "{{ item }}"
  state: present
  loop:

  * ncdu
    when: web_environment == "producción"

Resultado:

lab1
│
├── web_environment = producción
│
└── ncdu → instalado

lab2
│
├── web_environment = Development
│
└── ncdu → skipping

## LOOP + VARIABLES

Una lista también puede guardarse en una variable.

Ejemplo en:

group_vars/web.yml

web_packages:

* curl
* vim
* tree

Después se puede utilizar directamente en el loop:

* name: Instalar paquetes desde variable
  ansible.builtin.apt:
  name: "{{ item }}"
  state: present
  loop: "{{ web_packages }}"

## FLUJO

web_packages
│
├── curl
├── vim
└── tree
↓
loop
↓
item = curl
item = vim
item = tree

## IMPORTANTE

Esto:

loop:

* web_packages

NO utiliza la variable.

Simplemente crea una lista cuyo único elemento es el texto:

"web_packages"

Para utilizar una variable que contiene una lista:

loop: "{{ web_packages }}"

## REGLA MENTAL

Si el loop contiene valores simples:

loop:

* curl
* vim

Se utiliza:

{{ item }}

Si el loop contiene diccionarios:

loop:

* ruta: ...
  contenido: ...

Se utiliza:

{{ item.ruta }}

{{ item.contenido }}

Si la lista está guardada en una variable:

web_packages:

* curl
* vim

Se utiliza:

loop: "{{ web_packages }}"

## CONCEPTOS APRENDIDOS

* loop
* item
* Loops simples
* Loops para instalar paquetes
* Loops para crear directorios
* Loops para crear archivos
* Listas
* Diccionarios
* Listas de diccionarios
* item.clave
* loop + when
* loop + variables
* Variables que contienen listas
* group_vars
* Indentación YAML
* Diferencia entre listas y parámetros de módulos

## IDEA PRINCIPAL DEL EX05

Una misma tarea puede ejecutarse múltiples veces cambiando únicamente el valor de:

item

La evolución es:

TAREA
+
LISTA
↓
LOOP
↓
ITEM
↓
AUTOMATIZACIÓN REPETITIVA

## CONCEPTO FINAL

Loops simples:

item = valor

Loops con diccionarios:

item.clave = valor

↓

# BLOQUE 6 — TEMPLATES, JINJA2 Y VERIFICACIÓN

1. ¿QUÉ ES UN TEMPLATE EN ANSIBLE?

---

Un template permite generar un archivo dinámicamente utilizando variables y lógica Jinja2.

A diferencia de:

ansible.builtin.copy

que copia contenido estático, el módulo:

ansible.builtin.template

procesa las variables antes de generar el archivo en el servidor remoto.

Flujo:

Variables
↓
Template Jinja2
↓
Ansible procesa {{ variables }}
↓
Archivo generado en el servidor remoto

Ejemplo:

templates/index.html.j2

Servidor: {{ ansible_hostname }}
mensaje: {{ web_message }}
Entorno: {{ web_environment }}

Cada servidor puede generar un contenido diferente utilizando el mismo template.

2. ESTRUCTURA DEL PROYECTO

---

Una estructura típica es:

Certi/
│
├── hosts
├── site.yml
│
├── group_vars/
│   └── web.yml
│
├── host_vars/
│   ├── lab1.yml
│   └── lab2.yml
│
└── templates/
└── index.html.j2

Los templates se guardan habitualmente dentro del directorio:

templates/

3. USO DEL MÓDULO TEMPLATE

---

Ejemplo:

* name: Crear pagina web desde template
  ansible.builtin.template:
  src: index.html.j2
  dest: /var/www/html/index.html
  notify: reinicia nginx

Parámetros principales:

src
Archivo template en el controlador Ansible.

dest
Ruta donde se generará el archivo en el servidor remoto.

El módulo procesa las variables Jinja2 y genera el archivo final.

4. ERROR DE RUTA DEL TEMPLATE

---

Inicialmente se produjo el error:

Could not find or access '/templates/index.html.j2'

El problema era una ruta incorrecta del template.

En este proyecto, al utilizar el directorio estándar:

templates/

Ansible puede localizar automáticamente el archivo utilizando:

src: index.html.j2

Es importante diferenciar:

CONTROLADOR ANSIBLE
templates/index.html.j2

SERVIDOR REMOTO
/var/www/html/index.html

El template existe en el controlador.

El archivo generado existe en el servidor remoto.

5. VARIABLES EN UN TEMPLATE

---

Las variables se utilizan mediante:

{{ nombre_variable }}

Ejemplo:

Servidor: {{ ansible_hostname }}
mensaje: {{ web_message }}
Entorno: {{ web_environment }}

Al ejecutar el playbook, cada servidor genera su propio archivo utilizando sus variables.

Ejemplo conceptual:

lab1:

Servidor: debian
mensaje: Servidor gestionado por Ansible
Entorno: producción

lab2:

Servidor: lab2
mensaje: Servidor gestionado por Ansible
Entorno: Development

6. ERROR DE VARIABLE MAL ESCRITA

---

Se produjo el error:

'web_enviroment' is undefined

El problema era un error tipográfico.

Variable incorrecta:

web_enviroment

Variable correcta:

web_environment

Ansible detecta que la variable no existe y detiene la ejecución.

Es importante respetar exactamente el nombre de las variables.

7. CONDICIONES DENTRO DEL TEMPLATE CON JINJA2

---

Los templates utilizan Jinja2.

Jinja2 permite incluir condiciones directamente dentro del archivo.

Estructura:

{% if condicion %}

contenido si se cumple

{% else %}

contenido si no se cumple

{% endif %}

En este ejercicio se generó contenido diferente dependiendo de:

web_environment

Ejemplo conceptual:

{% if web_environment == "producción" %}

ESTE SERVIDOR ES DE PRODUCCIÓN

{% else %}

ESTE SERVIDOR ES DE DESARROLLO

{% endif %}

## IMPORTANTE SOBRE LAS COMILLAS

Al comparar una variable con un valor de texto dentro del template, el valor de texto debe ir entre comillas.

Ejemplo correcto:

{% if web_environment == "producción" %}

El valor:

"producción"

es una cadena de texto.

Si no se indican correctamente las comillas, Jinja puede intentar interpretar el valor como otra variable o expresión y producir un error.

Por tanto, para comparar con un texto:

CORRECTO:

{% if web_environment == "producción" %}

INCORRECTO:

{% if web_environment == producción %}

La condición debe tratar:

producción

como texto y no como una variable.

Flujo:

web_environment
↓
Jinja2 evalúa condición
↓
¿Es igual a "producción"?
│
├── Sí
│     ↓
│   Mostrar mensaje de producción
│
└── No
↓
Mostrar mensaje de desarrollo

La lógica está dentro del template.

No es necesario crear un template diferente para cada servidor.

8. RESULTADO DEL TEMPLATE

---

Producción:

Servidor: debian
mensaje: Servidor gestionado por Ansible
Entorno: producción
ESTE SERVIDOR ES DE PRODUCCIÓN

Desarrollo:

Servidor: lab2
mensaje: Servidor gestionado por Ansible
Entorno: Development
ESTE SERVIDOR ES DE DESARROLLO

El mismo template genera contenido diferente dependiendo de las variables del host.

9. NOTIFY Y HANDLERS

---

La tarea del template utiliza:

notify: reinicia nginx

Esto provoca que el handler solo se ejecute si el template modifica el archivo.

Ejemplo:

handlers:

* name: reinicia nginx
  ansible.builtin.service:
  name: nginx
  state: restarted

Primera ejecución:

Template cambia
↓
notify
↓
Handler reinicia nginx

Segunda ejecución sin cambios:

Template no cambia
↓
Handler no se ejecuta

Esto ayuda a mantener la automatización idempotente.

10. VERIFICAR EL ARCHIVO GENERADO

---

Después de generar el template, se puede verificar su contenido utilizando:

ansible.builtin.command

Ejemplo:

* name: Verificar el resultado generado
  ansible.builtin.command:
  cmd: cat /var/www/html/index.html
  register: comprobante
  changed_when: false

El resultado del comando se guarda en:

comprobante

11. REGISTER

---

register permite guardar el resultado de una tarea en una variable.

Ejemplo:

register: comprobante

La variable contiene información como:

comprobante.rc
comprobante.stdout
comprobante.stderr
comprobante.stdout_lines
comprobante.changed

Ejemplo:

rc
Código de salida.

stdout
Salida estándar completa.

stderr
Salida de error.

stdout_lines
Salida dividida por líneas.

12. CHANGED_WHEN: FALSE

---

El comando:

cat /var/www/html/index.html

solo consulta información.

No modifica el servidor.

Sin embargo, ansible.builtin.command puede marcar la tarea como:

changed

Para indicar correctamente que la tarea es solamente una comprobación se utiliza:

changed_when: false

Ejemplo:

* name: Verificar el resultado generado
  ansible.builtin.command:
  cmd: cat /var/www/html/index.html
  register: comprobante
  changed_when: false

Resultado:

ok

en lugar de:

changed

Principio importante:

Ejecutar un comando no significa necesariamente modificar el sistema.

13. MOSTRAR SOLO LA INFORMACIÓN RELEVANTE

---

Inicialmente se utilizó:

ansible.builtin.debug:
var: comprobante

Esto muestra toda la estructura:

cmd
delta
start
end
rc
stdout
stderr
changed
...

Si solo interesa mostrar el contenido del archivo es más limpio utilizar:

* name: Mostrar comprobante
  ansible.builtin.debug:
  msg: "{{ comprobante.stdout }}"

Esto muestra únicamente la salida estándar.

14. LOS SALTOS DE LÍNEA EN DEBUG

---

Al mostrar:

{{ comprobante.stdout }}

Ansible puede representar los saltos de línea como:

\n

Ejemplo:

"Servidor: debian\nmensaje: ..."

Esto no significa necesariamente que el archivo esté mal generado.

El contenido real puede comprobarse mediante un comando ad-hoc:

ansible web -i hosts -m ansible.builtin.command -a "cat /var/www/html/index.html"

Resultado:

Servidor: debian
mensaje: Servidor gestionado por Ansible
Entorno: producción
ESTE SERVIDOR ES DE PRODUCCIÓN

lab2:

Servidor: lab2
mensaje: Servidor gestionado por Ansible
Entorno: Development
ESTE SERVIDOR ES DE DESARROLLO

15. RESULTADO FINAL DEL BLOQUE

---

En este bloque se han combinado:

Variables
+
group_vars
+
host_vars
+
Templates
+
Jinja2
+
Condiciones dentro del template
+
Comparación de cadenas de texto con comillas
+
template
+
notify
+
handlers
+
command
+
register
+
changed_when
+
debug

Flujo completo:

Variables
↓
Template Jinja2
↓
Condición según entorno
↓
Comparación correcta del texto entre comillas
↓
Generar index.html diferente por servidor
↓
Desplegar mediante template
↓
Notificar al handler
↓
Reiniciar nginx si hubo cambios
↓
Leer el archivo generado
↓
Guardar resultado con register
↓
changed_when: false
↓
Mostrar resultado relevante

## CONCLUSIÓN

Un template permite generar archivos dinámicos a partir de variables y lógica Jinja2.

El mismo template puede producir resultados diferentes para distintos servidores.

Las condiciones Jinja2 permiten introducir lógica directamente dentro del archivo generado.

Cuando se compara una variable con un valor de texto, el valor debe tratarse como una cadena y utilizar correctamente las comillas.

register permite almacenar el resultado de una tarea para utilizarlo posteriormente.

changed_when permite corregir el estado mostrado por Ansible cuando una tarea realiza una comprobación pero no modifica el sistema.

La combinación de templates, variables, condiciones y verificación permite construir automatizaciones dinámicas, reutilizables e idempotentes.





# BLOQUE 7 — ROLES EN ANSIBLE

## OBJETIVO

Aprender a organizar un proyecto de Ansible utilizando Roles.

Hasta ahora, la mayor parte de las tareas se encontraban dentro de:

site.yml

Un Role permite agrupar todo lo relacionado con una responsabilidad concreta.

Ejemplo:

Role: web

Responsabilidad:

Configurar un servidor web.

## CONCEPTO PRINCIPAL

Un Playbook y un Role tienen responsabilidades diferentes.

site.yml
↓
Orquesta la ejecución

Role
↓
Contiene la implementación de una responsabilidad

Ejemplo:

site.yml
↓
Aplicar Role web
↓
El Role configura nginx

---

1. ESTRUCTURA DE UN ROLE

---

La estructura utilizada fue:

roles/
└── web/
├── tasks/
│   └── main.yml
│
├── handlers/
│   └── main.yml
│
└── templates/
└── index.html.j2

Cada directorio tiene una responsabilidad.

tasks/

Contiene las tareas del Role.

handlers/

Contiene los handlers del Role.

templates/

Contiene los templates utilizados por el Role.

---

2. TASKS/MAIN.YML

---

Dentro de:

roles/web/tasks/main.yml

se colocan directamente las tareas.

Ejemplo conceptual:

---

* name: Tarea 1
  ...

* name: Tarea 2
  ...

## ERROR COMETIDO

Inicialmente se intentó utilizar:

---

tasks:

* name: Instalar nginx
  ...

Esto es incorrecto dentro de:

roles/web/tasks/main.yml

El archivo ya se encuentra dentro del contexto:

tasks/

Por tanto, Ansible ya sabe que el contenido son tareas.

CORRECTO:

---

* name: Instalar nginx
  ...

* name: Otra tarea
  ...

## CONCEPTO

En un Playbook:

Play
↓
tasks:
↓
Lista de tareas

En un Role:

tasks/main.yml
↓
Lista directa de tareas

No es necesario volver a declarar:

tasks:

---

3. TAREAS DEL ROLE WEB

---

El Role web se encargó de:

1. Instalar nginx.

2. Habilitar nginx.

3. Arrancar nginx.

4. Generar la página web utilizando un template.

Conceptualmente:

Role web
↓
Instalar nginx
↓
Habilitar nginx
↓
Arrancar nginx
↓
Generar index.html

Esto permite encapsular toda la responsabilidad de configurar un servidor web.

---

4. HANDLERS/MAIN.YML

---

Los handlers también pueden pertenecer directamente a un Role.

Archivo:

roles/web/handlers/main.yml

## ERROR COMETIDO

Inicialmente se utilizó:

handlers:

* name: reinicia nginx
  ...

Esto es incorrecto dentro de:

handlers/main.yml

Al igual que ocurre con:

tasks/main.yml

el contexto ya viene definido por el directorio.

CORRECTO:

---

* name: reinicia nginx
  ansible.builtin.service:
  name: nginx
  state: restarted

## CONCEPTO

Playbook:

handlers:

* handler

Role:

handlers/main.yml
↓
Lista directa de handlers

No es necesario volver a declarar:

handlers:

---

5. RELACIÓN ENTRE TASKS Y HANDLERS

---

Una tarea del Role puede notificar a un handler del mismo Role.

Flujo:

tasks/main.yml
│
│ notify
▼
handlers/main.yml
│
▼
reinicia nginx

Ejemplo conceptual:

Tarea modifica template
↓
notify: reinicia nginx
↓
Handler marcado
↓
Finaliza la ejecución de tareas
↓
Handler reinicia nginx

El handler solamente debe ejecutarse cuando se produce un cambio en una tarea que lo notifica.

---

6. TEMPLATES DENTRO DE UN ROLE

---

El template fue movido a:

roles/web/templates/index.html.j2

Desde una tarea dentro del mismo Role se puede utilizar:

src: index.html.j2

No es necesario utilizar:

roles/web/templates/index.html.j2

El Role proporciona un contexto de búsqueda para sus propios recursos.

Conceptualmente:

Role web
│
├── tasks/main.yml
│
└── templates/
└── index.html.j2

La tarea del Role puede encontrar automáticamente:

index.html.j2

dentro del directorio:

templates/

---

7. FALLO REAL DEL TEMPLATE

---

Después de mover correctamente el template al Role, el Playbook falló con:

Could not find or access 'index.html.j2'

Ansible indicó que estaba buscando el archivo en:

/home/bertophoto/ansible/Certi/templates/index.html.j2

y:

/home/bertophoto/ansible/Certi/index.html.j2

El error también indicaba:

Origin: /home/bertophoto/ansible/Certi/site.yml

## CAUSA DEL ERROR

La tarea:

Crear pagina web desde template

seguía existiendo dentro de:

site.yml

Pero el archivo:

index.html.j2

había sido movido a:

roles/web/templates/index.html.j2

Por tanto existían dos tareas conceptualmente iguales:

ROLE WEB

roles/web/tasks/main.yml
↓
Crear pagina web desde template
↓
Busca el template dentro del contexto del Role

SITE.YML

site.yml
↓
Crear pagina web desde template
↓
Busca el template dentro del contexto del Playbook

La tarea dentro del Role encontraba correctamente:

roles/web/templates/index.html.j2

Pero la tarea antigua dentro de:

site.yml

intentaba buscar:

Certi/templates/index.html.j2

que ya no existía.

## SOLUCIÓN CONCEPTUAL

La tarea del template pertenecía a la responsabilidad:

Configurar servidor web

Por tanto, ya estaba correctamente ubicada dentro del Role:

web

La tarea antigua que permanecía en:

site.yml

estaba duplicada y debía eliminarse.

## CONCEPTO APRENDIDO

Al mover funcionalidad desde un Playbook a un Role hay que comprobar que no quedan tareas antiguas duplicadas.

Antes:

site.yml
└── Crear template

Después:

site.yml
↓
Aplica Role web
↓
└── Crear template

No deben mantenerse ambas tareas si realizan exactamente la misma función.

---

8. CONTEXTO DE BÚSQUEDA DE ARCHIVOS

---

El mismo:

src: index.html.j2

puede buscar en lugares diferentes dependiendo del contexto.

Dentro del Role:

roles/web/tasks/main.yml

Ansible busca los recursos del Role, incluyendo:

roles/web/templates/

Fuera del Role, desde:

site.yml

Ansible utiliza las rutas de búsqueda correspondientes al Playbook.

Por eso es importante saber:

DÓNDE se encuentra la tarea

y

DÓNDE se encuentra el recurso.

Flujo conceptual:

Tarea dentro del Role
↓
Contexto del Role
↓
Busca templates del Role

Tarea dentro de site.yml
↓
Contexto del Playbook
↓
Busca templates del Playbook

---

9. SITE.YML COMO ORQUESTADOR

---

Después de utilizar Roles, el:

site.yml

puede simplificarse.

Su función principal pasa a ser:

Seleccionar servidores
↓
Definir privilegios
↓
Aplicar Roles
↓
Ejecutar tareas adicionales

Conceptualmente:

site.yml
│
├── hosts
│
├── become
│
├── roles
│   └── web
│
└── tasks
└── Comprobaciones adicionales

El Playbook puede seguir conteniendo tareas directas.

Roles y tasks pueden convivir.

---

10. CONVIVENCIA ENTRE ROLES Y TASKS

---

Es posible utilizar:

roles:

y:

tasks:

dentro del mismo Play.

Conceptualmente:

Play
│
├── hosts
│
├── become
│
├── roles
│   └── web
│
└── tasks
├── comprobaciones
├── register
├── debug
├── when
└── otros ejercicios

Esto permite reutilizar un Role y, al mismo tiempo, ejecutar tareas específicas.

---

11. REGLA PARA IDENTIFICAR QUÉ PERTENECE A UN ROLE

---

Una buena pregunta es:

¿Esta tarea forma parte de la responsabilidad del Role?

Ejemplo:

Role web:

Instalar nginx
Configurar nginx
Generar contenido web
Gestionar handlers relacionados

Mientras que tareas genéricas o específicas de un ejercicio pueden permanecer temporalmente en:

site.yml

---

12. ESTRUCTURA FINAL CONCEPTUAL

---

Proyecto:

Certi/
│
├── hosts
│
├── site.yml
│
├── group_vars/
│
├── host_vars/
│
└── roles/
└── web/
│
├── tasks/
│   └── main.yml
│
├── handlers/
│   └── main.yml
│
└── templates/
└── index.html.j2

Flujo:

site.yml
↓
Selecciona hosts
↓
Aplica Role web
↓
tasks/main.yml
↓
Configura nginx
↓
Utiliza template
↓
Template modificado
↓
notify
↓
handlers/main.yml
↓
Reinicia nginx

---

13. CONCEPTOS APRENDIDOS

---

Roles
↓
Agrupan una responsabilidad.

tasks/main.yml
↓
Contiene directamente una lista de tareas.

handlers/main.yml
↓
Contiene directamente una lista de handlers.

templates/
↓
Contiene los templates del Role.

site.yml
↓
Orquesta la ejecución.

roles y tasks
↓
Pueden convivir dentro del mismo Play.

Contexto
↓
Influye en dónde Ansible busca archivos.

Refactorización
↓

---

## CONCLUSIÓN

Un Role permite transformar un Playbook grande en una estructura más modular y reutilizable.

La idea principal es separar:

ORQUESTACIÓN

de

IMPLEMENTACIÓN.

site.yml
↓
Decide qué se ejecuta y sobre qué servidores.

Role
↓
Contiene cómo se implementa una responsabilidad.

En este bloque se ha aprendido además un error práctico importante:

Mover un template al directorio de un Role no actualiza automáticamente las tareas antiguas que permanecen en site.yml.

Si una tarea sigue ejecutándose desde site.yml, Ansible buscará el template utilizando el contexto del Playbook.

Por tanto, al refactorizar un proyecto hacia Roles es necesario revisar:

* Qué tareas se han movido.
* Qué archivos se han movido.
* Qué handlers se han movido.
* Si existen tareas duplicadas.
* Desde qué contexto se están buscando los recursos.
