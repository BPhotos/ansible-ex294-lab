MINI DOCUMENTACION - EX01 ANSIBLE
======================================
Fundamentos vistos en el primer laboratorio EX294


1. INVENTARIO
-------------

El inventario define los hosts gestionados por Ansible y permite organizarlos
en grupos.

Ejemplo:

[web]
lab1
lab2

[db]
db01

Si un play contiene:

hosts: web

Ansible trabajara sobre lab1 y lab2, pero no sobre db01.

Idea clave:
    Inventario = donde y sobre quien trabajo.


2. PLAYBOOK -> PLAY -> TASK -> MODULE
-------------------------------------

La estructura conceptual es:

Playbook
  |
  +-- Play
       |
       +-- Task -> Module
       +-- Task -> Module
       +-- Task -> Module

Un play define, entre otras cosas:
- sobre que hosts se ejecuta
- si utiliza privilegios elevados
- que tareas debe realizar

Una task representa una accion.

Un module es el mecanismo de Ansible que realiza esa accion.


3. FQCN
-------

FQCN significa Fully Qualified Collection Name.

Ejemplos utilizados:

ansible.builtin.apt
ansible.builtin.copy
ansible.builtin.service

Durante la preparacion utilizaremos preferentemente FQCN.

Ejemplo:

ansible.builtin.apt:
  name: nginx
  state: present


4. BECOME
---------

become: true

Indica que las tareas necesitan ejecutarse con privilegios elevados en el managed node, normalmente mediante sudo.

No debe entenderse como una opcion que siempre hay que poner, sino como una forma de indicar que una operacion requiere privilegios.

5. FACTS
--------

Ansible puede recopilar informacion del sistema remoto antes de ejecutar las tareas.

Una forma de consultar los facts es:

ansible web -i hosts -m ansible.builtin.setup

Uno de los datos disponibles puede utilizarse como:

{{ ansible_hostname }}

Esto permite que el mismo playbook se adapte a diferentes servidores.

Ejemplo:

content: "Servidor: {{ ansible_hostname }}"

En lab1:

Servidor: lab1

En lab2:

Servidor: lab2


6. VARIABLES Y JINJA2
---------------------

Las variables permiten utilizar informacion dinamica en lugar de escribir valores fijos.

La sintaxis basica utilizada en este ejercicio es:

{{ variable }}

Ejemplo:

{{ ansible_hostname }}

Jinja2 se utiliza para interpolar y generar contenido dinamicamente.

En este primer laboratorio solo hemos utilizado una forma sencilla de Jinja2. Su estudio avanzado se realizara posteriormente.


7. MODULE COPY
--------------

ansible.builtin.copy permite copiar archivos o generar contenido.

En el ejercicio se utilizo:

ansible.builtin.copy:
  content: "Servidor: {{ ansible_hostname }}"
  dest: /var/www/html/index.html

La opcion content permite generar directamente el contenido del archivo.

Esto evita tener que crear manualmente un index diferente para cada servidor.


8. HANDLERS
-----------

Los handlers son tareas especiales que se ejecutan cuando una task las notifica mediante notify.

Ejemplo:

Task:

- name: Crear pagina web
  ansible.builtin.copy:
    content: "Servidor: {{ ansible_hostname }}"
    dest: /var/www/html/index.html
  notify: reinicia nginx

Handler:

handlers:
  - name: reinicia nginx
    ansible.builtin.service:
      name: nginx
      state: restarted

Conceptualmente:

TASK
 |
 +-- no cambia -> no handler
 |
 +-- cambia ----> notify -> HANDLER

El nombre de notify debe coincidir con el nombre del handler.

Error cometido durante el laboratorio:

notify: reinicia apache

Handler:

name: reinicia nginx

Resultado:

The requested handler 'reinicia apache' was not found

La correccion fue hacer coincidir ambos nombres.


9. IDEMPOTENCIA
---------------

Una de las ideas fundamentales de Ansible.

El objetivo no es ejecutar comandos repetidamente, sino conseguir que el sistema alcance un estado deseado.

Ejemplo:

ansible.builtin.apt:
  name: nginx
  state: present

Primera ejecucion:
    changed

Siguiente ejecucion:
    ok

En el laboratorio:

lab1 : changed=0
lab2 : changed=0

Esto demuestra que el sistema ya estaba en el estado declarado y Ansible no realizo cambios innecesarios.

Idea clave:

NO:
    "Ejecuta este comando."

SI:
    "Quiero que el sistema este en este estado."


10. SERVICIOS
-------------

ansible.builtin.service permite gestionar servicios.

Ejemplo:

- name: Configurar nginx
  ansible.builtin.service:
    name: nginx
    state: started
    enabled: yes

state: started
    Garantiza que el servicio este arrancado.

enabled: yes
    Garantiza que el servicio este habilitado para arrancar con el sistema.


11. TROUBLESHOOTING
-------------------

Ansible proporciona informacion muy util cuando una tarea falla.

Proceso recomendado:

1. Leer el error completo.
2. Identificar la TASK que falla.
3. Revisar que intenta hacer.
4. Revisar modulo y parametros.
5. Revisar variables.
6. Revisar nombres.
7. Revisar YAML e indentacion.
8. Corregir.
9. Ejecutar de nuevo.
10. Verificar el resultado.

Ejemplo real del laboratorio:

The requested handler 'reinicia apache' was not found

La causa no era nginx ni SSH.

Era una discrepancia entre:

notify: reinicia apache y name: reinicia nginx

Esto es troubleshooting basico de Ansible.


12. DOCUMENTACION
-----------------

No es necesario memorizar toda la sintaxis.

Durante la preparacion:

1. Intentar resolver.
2. Consultar documentacion oficial si falta sintaxis.
3. Aplicar la informacion encontrada.
4. Ejecutar.
5. Analizar el resultado.

La habilidad importante es saber que concepto/modulo necesitas y encontrar rapidamente la informacion correcta.


13. MODELO MENTAL
-----------------

Cuando recibas un problema de Ansible, pensar:

    ¿Sobre que servidores? --> INVENTARIO --> ¿Que estado quiero? --> PLAY --> ¿Que Acciones? --> TASK --> ¿Que modulo? --> MODULE --> ¿Necesito datos dinamicos? --> FACTS / VARIABLES --> ¿Una tarea cambia algo? --> NOTIFY --> HANDLER --> ¿Es idempotente? --> EJECTUAR DE NUEVO.

# EX02 - VARIABLES, GROUP_VARS Y FACTS
======================================

El objetivo de este ejercicio ha sido aprender a separar la configuración y los datos de la lógica del playbook.

En lugar de escribir toda la información directamente dentro de site.yml, una parte de la configuración se almacena en una variable externa.

## ESTRUCTURA FINAL

Certi/
├── apuntes.txt
├── enunciados.txt
├── group_vars/
│   └── web.yml
├── hosts
└── site.yml

## GROUP_VARS

Ansible permite definir variables asociadas a grupos del inventario.

Si en el inventario existe:

[web]
lab1
lab2

Podemos crear:

group_vars/web.yml

Las variables definidas dentro de ese archivo estarán disponibles automáticamente para los hosts pertenecientes al grupo web.

## VARIABLE UTILIZADA

En group_vars/web.yml:

	---
	web_message: "Servidor gestionado por Ansible"

Esta variable se puede utilizar posteriormente desde el playbook: {{ web_message }}

## SEPARACION DE CONFIGURACION Y LOGICA

Antes:

site.yml
|
+-- Contenido fijo
+-- Lógica del playbook

Ahora:

group_vars/web.yml
|
+-- Datos / configuración

site.yml
|
+-- Lógica / automatización

Esto permite que los playbooks sean más mantenibles.

Si necesitamos modificar el mensaje, podemos hacerlo sin modificar la lógica del playbook.

## USO DE VARIABLES

Las variables se utilizan mediante Jinja:

{{ nombre_variable }}

Ejemplo:

{{ web_message }}

## FACTS DE ANSIBLE

Ansible recopila información sobre los hosts remotos durante:

Gathering Facts

Una de esas variables es:

ansible_hostname

Ejemplo:

{{ ansible_hostname }}

Esta variable devuelve el hostname real configurado en el sistema remoto.

## VARIABLE PROPIA + FACT

En el ejercicio se combinaron:

ansible_hostname y web_message

para generar dinámicamente el contenido de:

/var/www/html/index.html

DIFERENCIA IMPORTANTE:
INVENTORY HOSTNAME VS ANSIBLE_HOSTNAME
--------------------------------------

Durante el ejercicio se descubrió que nombre del host en el inventario no siempre es igual a ansible_hostname

Ejemplo:

INVENTARIO              HOSTNAME REAL
---
lab1                    debian
lab2                    lab2

Por tanto:

lab1 es el nombre utilizado por Ansible dentro del inventario.
Mientras que ansible_hostname representa el hostname configurado realmente en el sistema operativo remoto.

## COMPROBAR VARIABLES

Podemos comprobar directamente una variable utilizando:

ansible web -i hosts -m ansible.builtin.debug -a "var=web_message"
Esto permite verificar que Ansible está cargando correctamente la variable.

Resultado esperado:

lab1 → Servidor gestionado por Ansible
lab2 → Servidor gestionado por Ansible

## COMPROBAR EL INVENTARIO
Podemos visualizar la estructura del inventario:

ansible-inventory -i hosts --graph

También podemos obtener una representación completa:
ansible-inventory -i hosts --list

## GENERAR CONTENIDO DINAMICO

El módulo copy permite generar un archivo utilizando variables.

Ejemplo conceptual:

ansible.builtin.copy:
content: "Servidor: {{ ansible_hostname }}\n{{ web_message }}"
dest: /var/www/html/index.html

## IMPORTANTE: SALTOS DE LINEA

Durante el ejercicio apareció un problema con el salto de línea.

Se utilizó: \\n Esto provocó que el contenido generado mostrase literalmente: Servidor: lab2\nServidor gestionado por Ansible

Para generar un salto de línea real debe utilizarse: \n

VERIFICACION DEL RESULTADO REAL
-------------------------------

Un PLAY RECAP correcto no significa necesariamente que el resultado final sea exactamente el esperado.
Después de ejecutar el playbook se comprobó el contenido real: ansible web -i hosts -m ansible.builtin.command -a "cat /var/www/html/index.html"

Esto permitió descubrir:

1. Que el salto de línea se estaba escribiendo incorrectamente.
2. Que lab1 y ansible_hostname no tenían el mismo valor.

LECCION IMPORTANTE
------------------

No debemos considerar un playbook correcto únicamente porque: failed=0

También debemos comprobar que el estado final del sistema es realmente el esperado.

HANDLERS
--------

Se mantuvo el handler aprendido en EX01.

La tarea que modifica index.html notifica al handler: notify: reinicia nginx

El handler solamente se ejecuta cuando la tarea produce un cambio.

Si index.html no cambia:

	- la tarea devuelve ok;
	- no se ejecuta el handler;
	- nginx no se reinicia.

IDEMPOTENCIA
------------

Primera ejecución:

La página web cambió.

Por tanto:

	- la tarea copy produjo changed;
	- se notificó el handler;
	- nginx se reinició.


Segunda ejecución: changed=0

Esto demuestra que el playbook es idempotente.

El estado deseado ya estaba configurado y Ansible no realizó cambios innecesarios.

# EX03 - HOST_VARS Y TAREAS CONDICIONALES

## OBJETIVO

Aprender a utilizar variables específicas por host y tomar decisiones diferentes dentro del mismo playbook.

Hasta ahora se utilizaban variables comunes para todos los servidores de un grupo mediante:

group_vars/

## ESTRUCTURA

Para definir variables específicas de cada host:

host_vars/
├── lab1.yml
└── lab2.yml

Ejemplo:

host_vars/lab1.yml

---

web_environment: "producción"

host_vars/lab2.yml

---

web_environment: "Development"

## VARIABLES POR GRUPO VS VARIABLES POR HOST

group_vars:

Una variable se aplica a todos los hosts del grupo.

Ejemplo:

group_vars/web.yml

---

web_message: "Servidor gestionado por Ansible"

host_vars:

Una variable se aplica únicamente al host cuyo nombre coincide con el archivo.

Ejemplo:

host_vars/lab1.yml

---

web_environment: "producción"

host_vars/lab2.yml

---

web_environment: "Development"

## COMPROBAR VARIABLES

Se puede comprobar el valor de una variable con:

ansible web -i hosts -m ansible.builtin.debug -a "var=web_environment"

## USO DE VARIABLES EN EL PLAYBOOK

Las variables se utilizan mediante Jinja:

{{ variable }}

Ejemplo:

content: "Servidor: {{ ansible_hostname }}
{{ web_message }}
{{ web_environment }}"

## TAREAS CONDICIONALES

Ansible permite ejecutar tareas únicamente cuando se cumple una condición mediante:

when:

Ejemplo:

* name: Crear archivo de producción
  ansible.builtin.copy:
  content: "Este servidor es de PRODUCCIÓN"
  dest: /var/www/html/production.txt
  when: web_environment == "producción"

La tarea solo se ejecutará cuando la variable tenga ese valor.

## CONDICIÓN INVERSA

También se puede ejecutar una tarea cuando la condición NO se cumple:

* name: Crear archivo de desarrollo
  ansible.builtin.copy:
  content: "Este servidor NO es PRODUCCION"
  dest: /var/www/html/development.txt
  when: web_environment != "producción"

## OPERADORES IMPORTANTES

Igual:

==

Distinto:

!=

Ejemplos:

when: web_environment == "producción"

when: web_environment != "producción"

## RESULTADO POR HOST

El mismo playbook puede comportarse de forma diferente dependiendo de las variables de cada host.

Ejemplo:

lab1
│
└── web_environment = producción
│
└── production.txt

lab2
│
└── web_environment = Development
│
└── development.txt

## SKIPPING

Cuando una condición when no se cumple, Ansible muestra:

skipping

Esto no es un error.

Significa:

La tarea existe
↓
Ansible evalúa la condición
↓
La condición es falsa
↓
La tarea no se ejecuta

## CONCEPTO PRINCIPAL DEL EX03

Un único playbook puede gestionar diferentes servidores de forma diferente.

La lógica es:

Variables
↓
Identificar características del host
↓
when
↓
Ejecutar únicamente las tareas necesarias

## CONCEPTOS APRENDIDOS

* group_vars
* host_vars
* Variables específicas por host
* Variables comunes por grupo
* Uso de {{ variable }}
* when
* ==
* !=
* Tareas condicionales

No es necesario crear un playbook diferente para cada servidor.

Se puede utilizar:

para adaptar la automatización a cada host.


# EX04 - REGISTER, RESULTADOS Y DECISIONES

## OBJETIVO

Aprender a ejecutar una comprobación, guardar el resultado y utilizar esa información para tomar decisiones dentro del playbook.

El patrón principal es:

COMPROBAR
↓
EJECUTAR
↓
REGISTER
↓
ANALIZAR RESULTADO
↓
WHEN
↓
ACTUAR

## REGISTER

register permite guardar el resultado de una tarea dentro de una variable.

Ejemplo:

* name: Comprobar si existe nginx
  ansible.builtin.command:
  cmd: ls -lrt /usr/sbin/nginx
  register: nginx_check

Después de ejecutar la tarea, Ansible guarda el resultado en:

nginx_check

## EL RESULTADO DE REGISTER

Una variable registrada no contiene únicamente un resultado simple.

Puede contener información como:

nginx_check
│
├── rc
├── stdout
├── stdout_lines
├── stderr
├── stderr_lines
├── changed
├── failed
├── cmd
├── start
├── end
└── delta

## CODIGO DE RETORNO

El campo:

rc

significa Return Code.

Normalmente:

rc = 0

significa que el comando se ejecutó correctamente.

Ejemplo:

* name: Mostrar código de retorno
  ansible.builtin.debug:
  msg: "{{ nginx_check.rc }}"

Si el resultado es:

msg: 0

significa que el comando terminó correctamente.

## USAR REGISTER CON WHEN

El resultado de una tarea puede utilizarse posteriormente en una condición.

Ejemplo:

* name: nginx está instalado
  ansible.builtin.debug:
  msg: "nginx esta instalado en este servidor"
  when: nginx_check.rc == 0

## CONDICIÓN INVERSA

También se puede actuar cuando el resultado es diferente.

Ejemplo:

* name: nginx no está instalado
  ansible.builtin.debug:
  msg: "nginx no esta instalado en este servidor"
  when: nginx_check.rc != 0

## FLUJO

Comando
↓
register
↓
nginx_check
↓
nginx_check.rc
↓
when
│
├── rc == 0
│       ↓
│    Ejecutar acción
│
└── rc != 0
↓
Ejecutar otra acción

## DEBUG

debug permite inspeccionar valores y variables.

Mostrar un valor concreto:

ansible.builtin.debug:
msg: "{{ nginx_check.rc }}"

Mostrar una variable completa:

ansible.builtin.debug:
var: comprobacion

Es especialmente útil utilizar:

var:

cuando todavía no sabemos qué campos contiene una variable registrada.

## EJEMPLO DE COMPROBACIÓN REAL

Comprobar la versión de nginx:

* name: Comprobar versión de nginx
  ansible.builtin.command:
  cmd: nginx -v
  register: comprobacion

Posteriormente:

* name: Mostrar resultado
  ansible.builtin.debug:
  var: comprobacion

## RESULTADO OBTENIDO

La variable registrada puede contener:

changed
cmd
delta
failed
rc
stdout
stderr

En la comprobación:

nginx -v

se obtuvo:

rc: 0

stderr: "nginx version: nginx/1.26.3"

stdout: ""

IMPORTANTE:

No todos los comandos escriben su información en stdout.

Algunos comandos escriben información en:

stderr

Por eso es recomendable inspeccionar primero el resultado completo mediante:

ansible.builtin.debug:
var: comprobacion

Después se puede acceder directamente al campo necesario:

{{ comprobacion.rc }}

{{ comprobacion.stdout }}

{{ comprobacion.stderr }}

## COMBINAR VARIABLES Y REGISTER

Se pueden combinar condiciones basadas en variables con resultados reales.

Ejemplo:

* name: Comprobar versión de nginx en producción
  ansible.builtin.command:
  cmd: nginx -v
  register: comprobacion
  when: web_environment == "producción"

Después:

* name: Mostrar comprobación
  ansible.builtin.debug:
  var: comprobacion
  when: web_environment == "producción"

## CONDICIONES COMPUESTAS

Se pueden combinar varias condiciones mediante:

and

Ejemplo:

when: nginx_check.rc == 0 and web_environment == "producción"

La tarea solo se ejecutará si ambas condiciones son verdaderas.

## FLUJO FINAL DEL EJERCICIO

lab1

web_environment = producción
↓
nginx -v
↓
register: comprobacion
↓
debug
↓
Mostrar información

lab2

web_environment = Development
↓
when = false
↓
skipping

## COMMAND Y CHANGED

Cuando se utiliza:

ansible.builtin.command

Ansible puede mostrar:

changed

aunque el comando únicamente haya realizado una comprobación.

Esto ocurre porque command ejecuta un comando, pero no conoce automáticamente si dicho comando ha modificado el estado real del sistema.

Por tanto:

changed

en una tarea command no siempre significa que el sistema haya cambiado.
